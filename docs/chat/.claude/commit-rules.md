# 커밋 규칙 — 팀원 보고용

## 커밋 시점
다음 중 하나라도 해당하면 즉시 커밋한다. 사용자에게 묻지 않아도 된다.
- 하나의 논리적 작업 단위가 완료되었을 때 (기능 1개, 버그 1개, 리팩토링 1건)
- 테스트가 통과한 직후
- 30분 이상 연속 작업이 진행되었고 중간 상태가 의미 있을 때
- 사용자가 "커밋해줘" 또는 "정리해줘"라고 말했을 때

여러 작업이 섞여 있다면 의미 단위로 **분할 커밋**한다. 한 커밋에 한 가지 일만 담는다.

## 커밋 메시지 형식

```
<type>: <50자 이내 한 줄 요약>

## 무엇을 했나
- 변경된 파일/모듈과 핵심 변경사항을 bullet로 나열
- 기능 추가/수정/삭제를 명확히 구분
- 비기술자 팀원도 이해할 수 있는 언어로

## 어떻게 구현했나
- 선택한 접근법과 그 이유
- 사용한 라이브러리/패턴/알고리즘
- 코드 구조상 주의할 점 (예: 의존성, 부수효과)

## 논의된 쟁점 / 결정사항
- 작업 중 고민했던 선택지들 (A vs B)
- 최종적으로 채택한 안과 그 근거
- 의도적으로 보류한 항목 (TODO/FIXME)
- 팀원이 리뷰 시 봐야 할 부분

## 다음 단계 (선택)
- 이 커밋 이후 이어질 작업
- 미해결 이슈
```

### type 종류
`feat` 새 기능 / `fix` 버그 수정 / `refactor` 리팩토링 / `docs` 문서 / 
`test` 테스트 / `chore` 빌드·설정 / `style` 포맷팅 / `perf` 성능 개선

## 작성 원칙

1. **사실 기반**: 실제로 한 일만 적는다. 안 한 일을 적지 않는다.
2. **이유 중심**: "무엇을"보다 "왜"가 더 중요하다. 코드를 보면 무엇을 했는지는 알 수 있지만, 왜 했는지는 메시지에만 남는다.
3. **쟁점은 솔직하게**: 막혔던 부분, 확신이 없는 부분, 트레이드오프가 있었던 부분을 숨기지 않는다. 팀원이 그걸 봐야 한다.
4. **분량**: 요약은 짧게, 본문은 충실하게. 사소한 변경(오타 수정 등)은 한 줄로 끝내도 된다.

## 커밋 전 확인
- `git status`와 `git diff --cached`로 staging 내용을 먼저 확인한다
- 의도하지 않은 파일(.env, 빌드 산출물 등)이 포함되지 않았는지 본다
- 한 커밋에 여러 관심사가 섞였다면 `git add -p`로 분할한다

## 커밋 후
- `git log -1 --stat` 결과를 사용자에게 보여준다
- push는 사용자가 명시적으로 요청할 때만 한다 (자동 push 금지)
